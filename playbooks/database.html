    Lesson 1 · 8 min

    AWS has a database for every data shape

    The exam rarely asks "how do I tune this database". It asks "which database fits this data and access pattern".

    OLTP: run the business

    Many small, fast reads and writes: orders, logins, carts. Row-based. RDS, Aurora, DynamoDB.

    OLAP: analyse the business

    Few huge queries over millions of rows: reports, BI dashboards. Columnar. Redshift (and Athena on S3).

    Lesson 2 · 15 min · heavily tested

    RDS: managed relational databases

    AWS handles hardware, OS, patching, backups and failover. You get a DNS endpoint, not SSH access.

    Backups

    automatic
    • Automated backups: retention 1–35 days (0 turns them off)
    • Point-in-time restore to any second, up to about 5 minutes ago
    • Manual snapshots: kept until you delete them
    • Copy snapshots and backups to other Regions
    • Every restore creates a new DB instance with a new endpoint

    Storage

    EBS
    • gp3 or io2 storage
    • Storage autoscaling: grows automatically up to a maximum you set
    • Can't shrink storage

    Security

    layers
    • In a VPC, private subnets, security groups
    • KMS encryption chosen at creation; replicas and snapshots inherit it
    • TLS in transit
    • IAM database authentication (MySQL, MariaDB, PostgreSQL): 15-minute token instead of a password
    • Passwords in Secrets Manager with rotation

    Operations

    know these
    • RDS Proxy: connection pooling (Lambda), faster failover
    • Blue/Green deployments: upgrade on a synced copy, switch over in about a minute
    • RDS Custom: Oracle / SQL Server with OS access
    • Parameter groups, maintenance window
    • Performance Insights to find slow queries

    Lesson 3 · 12 min

    Aurora: relational, rebuilt for the cloud

    MySQL- or PostgreSQL-compatible. The trick is storage: one shared volume with 6 copies across 3 AZs, used by the writer and all replicas.

    Storage quorum: break some copies

    Click a copy to fail or repair it. Writes need 4 of 6 copies, reads need 3 of 6. Aurora repairs bad copies automatically.

    Replicas and failover

    • Up to 15 Aurora replicas, lag usually milliseconds
    • A replica is promoted automatically, typically under 30 s
    • Set failover priority tiers
    • Replica Auto Scaling

    Endpoints

    • Cluster (writer) endpoint: always the current writer
    • Reader endpoint: load-balances across replicas
    • Custom endpoint: a chosen subset (e.g. bigger replicas for analytics)
    • Instance endpoints: one specific instance

    Aurora Serverless v2

    Capacity scales up and down in small steps (ACUs) within seconds. For variable or unpredictable workloads, dev/test, many tenants.

    "unpredictable", "intermittent", "scale automatically"

    Aurora Global Database

    1 primary Region + secondary read-only Regions. Storage-level replication, typically under 1 s lag. Promote a secondary in about a minute. Write forwarding lets secondaries send writes to the primary.

    Backtrack

    Aurora MySQL only. Rewind the cluster to a time (up to 72 h) in place, in minutes, without restoring a new cluster.

    Cloning

    Copy-on-write clone of a cluster in minutes. Perfect for a test copy of production data.

    Storage grows automatically, so you never provision it. Aurora I/O-Optimized pricing suits I/O-heavy workloads; Standard suits the rest.

    Lesson 4 · 15 min · heavily tested

    DynamoDB: serverless key-value at any scale

    No servers, no SQL joins, single-digit millisecond responses whether you have 1 GB or 1 PB.

    Table structure

    • Partition key (required): decides where data is stored. Pick high-cardinality values
    • Sort key (optional): orders items within a partition, allows range queries
    • Items up to 400 KB; attributes can differ per item

    Capacity modes

    • On-demand: pay per request, no planning. Unpredictable or spiky traffic
    • Provisioned: set RCU/WCU, add auto scaling. Predictable traffic, cheaper at steady load
    • Over the limit → ProvisionedThroughputExceededException

    Reads

    • Eventually consistent (default): cheapest, may be a moment stale
    • Strongly consistent: latest data, costs 2×
    • Transactional: all-or-nothing across items, costs 2× strong

    Capacity calculator

    Read type
    Read capacity units
    Write capacity units

    1 RCU = 1 strongly consistent read per second of up to 4 KB (or 2 eventually consistent). 1 WCU = 1 write per second of up to 1 KB. Always round the item size up first.

    Indexes

    Local secondary index (LSI)Global secondary index (GSI)
    KeysSame partition key, different sort keyAny partition key and sort key
    WhenOnly at table creationAny time
    ConsistencyStrong or eventualEventual only
    CapacityShares the table'sIts own (a throttled GSI can throttle table writes)
    Limit5 per table20 per table (default)

    DAX

    In-memory cache for DynamoDB: microsecond reads, same API, few code changes. Read-heavy, hot keys.

    Streams

    Ordered log of item changes, kept 24 h. Trigger Lambda on every insert, update or delete. Or stream to Kinesis Data Streams for longer retention.

    Global tables

    Multi-Region, multi-active: read and write in any Region, replicated in about a second. Last writer wins on conflicts.

    TTL

    Set an expiry timestamp per item; DynamoDB deletes it for free. Sessions, temporary tokens.

    Backups

    PITR: restore to any second in the last 35 days. On-demand backups kept until deleted. Restores go to a new table. Export to S3 for analytics with Athena.

    Security

    Always encrypted at rest. IAM fine-grained access (e.g. users see only items with their ID as key). Gateway VPC endpoint for private access.

    Caching needs app code changes (lazy loading or write-through). Security: VPC, security groups, AUTH token or IAM auth, encryption in transit and at rest.

    Redshift: the data warehouse

    How it works

    Columnar storage, massively parallel processing (leader node + compute nodes). Standard SQL, connects to BI tools like QuickSight.

    Redshift Spectrum

    Query data in S3 directly from Redshift, without loading it. Join warehouse tables with data lake files.

    Serverless & scaling

    Redshift Serverless: no clusters to size. Concurrency scaling: extra capacity for bursts of queries. RA3 nodes separate compute from managed storage.

    Loading data

    COPY from S3 (fastest bulk load), Data Firehose for streams, zero-ETL integrations from Aurora, RDS and DynamoDB.

    DR

    Automatic snapshots to S3; configure cross-Region snapshot copy for disaster recovery.

    Not for OLTP

    Slow for single-row inserts and lookups. "Transactions from the website" is never Redshift.

    Redshift vs Athena. Redshift: frequent, complex queries, dashboards, data loaded into a warehouse. Athena: serverless, ad-hoc SQL directly on S3, pay per TB scanned.

    Migration: DMS and SCT

    Database Migration Service

    Copies data from source to target while the source stays online. Full load, then CDC (change data capture) keeps them in sync until cut-over. Runs on a replication instance or DMS Serverless.

    Schema Conversion Tool

    Needed only when engines differ (heterogeneous, e.g. Oracle → Aurora PostgreSQL). Converts tables, views, stored procedures. Same engine (MySQL → RDS MySQL) needs no SCT. DMS Schema Conversion does this inside DMS.
