    Every migration question starts with a strategy: the 7 Rs

    The question tells you how much change the company accepts. "As quickly as possible, no code changes" is one end; "cloud-native, scale to millions" is the other.

    Which R is this?

    Pick a scenario.

    Discover and plan before moving

    Application Discovery Service

    inventory

    Collects server specs, utilization and dependencies from on-prem. Agentless collector (VMware) for inventory and performance; the agent adds running processes and network connections.

    Migration Hub

    track

    One place to track migration status across tools (MGN, DMS) and group servers into applications.

    Migration Evaluator

    business case

    Builds a cost / TCO case from on-prem usage: "how much would this cost on AWS?"

    Keywords: "lift and shift", "minimal changes", "quickly" → Rehost with MGN. "Move the database to a managed service but keep the app" → Replatform. "Replace with SaaS" → Repurchase.
    Lesson 2 · 10 min

    Moving servers: Application Migration Service

    AWS Application Migration Service (MGN)

    default answer
    • Agent on each source server does continuous block-level replication to a staging area in AWS
    • Launch test instances, then a short cutover: minutes of downtime
    • Physical, VMware, Hyper-V, other clouds
    • Replaced the old Server Migration Service (SMS) and CloudEndure Migration

    VM Import/Export

    images

    Import a VM image (OVA, VMDK, VHD) as an AMI, or export an instance back. One-off image conversion, no continuous replication.

    Elastic Disaster Recovery (DRS)

    DR, not migration

    Same replication technology as MGN, but keeps servers replicated for recovery: low RPO (seconds), RTO in minutes, pay for cheap staging until you fail over.

    Lift-and-shift 300 VMs with minimal downtimeMGN
    Bring one golden VM image into AWSVM Import/Export
    On-prem servers must fail over to AWS if the data center burnsElastic Disaster Recovery

    Moving databases: DMS and SCT

    DMS copies the data while the source keeps running. SCT converts the schema when the engine changes.

    SourceOn-prem Oracle / SQL Server / MySQL…Stays online during the migration
    DMS replicationReplication instance or DMS ServerlessFull load, then CDC (change data capture) keeps the target in sync
    TargetRDS, Aurora, Redshift, DynamoDB, S3, Kinesis…Cut over when lag is near zero
    Migration typeExampleSchema conversion?Tools
    HomogeneousMySQL → RDS for MySQL, Oracle → RDS for OracleNoDMS (or native dump/restore)
    HeterogeneousOracle → Aurora PostgreSQL, SQL Server → Aurora MySQLYesSCT (or DMS Schema Conversion) + DMS
    Into a warehouseOracle DW → RedshiftYesSCT (with data extraction agents) + DMS

    Continuous replication

    DMS with CDC can run for weeks: migrate, then keep syncing until cutover. Also used for ongoing replication into S3 or Kinesis.

    High availability

    Multi-AZ replication instance: a standby in another AZ for long-running tasks.

    Very large databases

    Slow link + many TB: load the initial copy offline (Snowball Edge), then let DMS CDC catch up.

    Not for

    DMS migrates data, not stored procedures logic or app code. SCT flags what needs manual work.

    Exam trap: Engine changes → SCT + DMS. Same engine → DMS alone. "Minimal downtime" → DMS with CDC, not a dump and restore.
    Lesson 4 · 15 min · heavily tested

    Moving files over the network

    DataSync

    bulk copy, scheduled
    • Agent on-prem reads NFS, SMB, HDFS, object storage, other clouds
    • Writes to S3 (any class), EFS, FSx; also copies between AWS storage services
    • Encryption in transit, integrity checks, keeps metadata and permissions
    • Scheduling, bandwidth throttling, incremental runs

    "migrate NFS share to EFS", "move file data to S3 on a schedule" → DataSync

    Transfer Family

    SFTP / FTPS / FTP / AS2

    Managed endpoint in front of S3 or EFS. Partners keep using their SFTP clients and scripts; you stop running FTP servers.

    "partners upload via SFTP" → Transfer Family

    Storage Gateway

    hybrid, ongoing
    • S3 File Gateway: NFS/SMB share, files stored as S3 objects, local cache
    • Volume Gateway: iSCSI. Cached: primary data in AWS. Stored: primary local, backed up to AWS as EBS snapshots
    • Tape Gateway: virtual tape library for existing backup software → S3 / Glacier

    S3 Transfer Acceleration

    long distance

    Uploads enter the nearest edge location and ride the AWS backbone to the bucket. Users far from the bucket's Region.

    Direct Connect

    private link

    Consistent bandwidth and lower egress price. Takes weeks to provision, so not for an urgent one-time move. Not encrypted by itself: add a VPN or MACsec.

    DataSync vs Storage Gateway: DataSync moves data (migration, periodic copies). Storage Gateway keeps on-prem apps working against cloud storage long term.

    Network or truck? Transfer-time calculator

    Network time = data × 8 ÷ (bandwidth × share used). Snowball Edge time is a rough end-to-end figure (order, ship, copy, return, import) of about a week; devices work in parallel.

    Lesson 5 · 8 min

    Offline transfer and the edge: Snow family

    Snowball Edge Storage Optimized

    TB → PB

    Rugged device shipped to you. Tens to 200+ TB per device; order several in parallel for petabytes. Data encrypted with KMS keys.

    Snowball Edge Compute Optimized

    edge compute

    More vCPUs (optional GPU) to run EC2 instances or Lambda functions at disconnected sites: ships, mines, field labs.

    Older names you may see

    exam history

    Snowcone: small (8–14 TB) device with a DataSync agent. Snowmobile: a truck for exabytes. AWS has stopped offering both to new customers, but older questions still use them.

    Snowball imports into S3Want Glacier? Import to S3, then a lifecycle rule moves it.
    Use when the network would take more than ~a weekOr bandwidth is shared with production, expensive, or unavailable.
    Manage with AWS OpsHubGUI to unlock, copy and monitor the device.
    Disconnected / limited connectivity siteEdge compute on Snowball Edge.
    Decision: small or ongoing → DataSync over internet/DX. Huge one-time and slow link → Snowball Edge. Ongoing hybrid access → Storage Gateway. SFTP partners → Transfer Family.
