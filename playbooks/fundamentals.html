    Where AWS runs: Regions, AZs and the edge

    Every resilience question comes back to this map. Know what each layer is, how far apart things are, and what fails together.

    Region

    isolated
    • A geographic area with at least three AZs
    • Fully independent of other Regions: data stays in the Region unless you copy it
    • Most services are Regional: you pick the Region per resource

    Availability Zone

    fault boundary
    • One or more data centers with their own power, cooling and networking
    • Physically separated (miles apart, within ~100 km) and linked by low-latency private fiber
    • Spread across ≥ 2 AZs to survive a data-center failure

    AZ names vs AZ IDs

    trap

    us-east-1a maps to a different physical AZ in each account. The AZ ID (use1-az1) is the same everywhere. Use AZ IDs to line up resources across accounts.

    Edge locations

    600+ PoPs

    Points of presence in many more cities than Regions. Run CloudFront, Route 53, Global Accelerator entry points, AWS WAF and Shield at the edge. You don't deploy servers there.

    Choosing a Region: four factors

    FactorQuestion to askExam wording
    Compliance / data residencyIs the data legally required to stay in a country?"data must not leave the EU" → that wins over everything
    LatencyWhere are most users?"users in Japan" → ap-northeast-1
    Service availabilityIs the service or feature launched there?New services arrive Region by Region
    PriceSame resource, different price per RegionTie-breaker once the others are met

    Global, Regional or zonal? Know what fails with what

    An AZ-scoped resource dies with its AZ. A Regional service already spreads across AZs. A global service has one control plane for every Region. Click each service to sort it.

    GlobalOne namespace / control plane for all Regions
      RegionalSpans the AZs of one Region
        Zonal (one AZ)Lives in a single AZ

          Pick a service.

          Consequences the exam tests: an EBS volume can only attach to instances in its own AZ (move it with a snapshot). AMIs and snapshots are Regional: copy them to another Region for DR. ACM certificates for CloudFront must be in us-east-1. S3 bucket names are global, but each bucket lives in one Region.
          Lesson 3 · 10 min

          Who patches what? The shared responsibility model

          AWS secures the cloud (facilities, hardware, hypervisor, global network). You secure what you put in the cloud. The line moves up as the service gets more managed.

          Service
          LayerWhoNote

          Always yours

          every service
          • Your data and how it's classified
          • IAM: who can access what
          • Choosing to encrypt, and managing keys you own
          • Configuration you set (bucket policies, security groups)

          Always AWS

          every service
          • Physical security of data centers
          • Hardware, storage devices, network infrastructure
          • Virtualization layer

          Shared controls

          both

          Patch management (AWS patches infrastructure, you patch guest OS and apps), configuration management, and awareness and training are done by both, each in their own layer.

          Lesson 4 · 12 min

          How you talk to AWS: tools, credentials and ARNs

          Console

          browser

          Web UI. Fine for learning and one-off tasks. Not repeatable.

          CLI & SDKs

          API

          Every action is an API call. CLI for scripts, SDKs (Python boto3, Java, JS…) inside apps. Both sign requests with your credentials.

          CloudShell

          no setup

          Browser shell already signed in as your console identity, CLI preinstalled, small persistent home directory per Region.

          CloudFormation

          IaC

          Templates (YAML/JSON) → stacks. Repeatable, versioned, rollback on failure. StackSets deploy to many accounts and Regions. CDK writes CloudFormation from code.

          Who / whereCredential to useAvoid
          App on EC2IAM role via instance profile (temporary keys)Access keys in code or on disk
          Lambda / ECS taskExecution role / task roleHard-coded keys
          Human on a laptopIAM Identity Center (SSO), aws configure ssoLong-lived IAM user keys
          Root userMFA, used only for root-only tasksRoot access keys, daily use

          ARN decoder

          Format: arn:partition:service:region:account-id:resource. Partition is aws, aws-cn or aws-us-gov. Global services (IAM) and S3 buckets leave some fields empty.

          Lesson 5 · 12 min

          Accounts, Organizations, quotas and support

          The account is the boundary

          An AWS account is a hard boundary for security, billing and quotas. Separate accounts for prod, dev and security limit the blast radius of a mistake.

          Root user

          • Turn on MFA, delete root access keys, lock it away
          • Only for root-only tasks: change the account's root email or password, close the account, enable S3 MFA Delete, restore IAM access if everyone is locked out
          • Everyday admin work → an IAM Identity Center or IAM identity with admin permissions

          AWS Organizations

          Root ├─ Management account billing, SCPs not applied ├─ OU: Security ── Log archive · Audit ├─ OU: Prod ── App-A prod · App-B prod └─ OU: Dev ── Sandboxes
          • Consolidated billing: one bill, pooled volume discounts, shared RIs and Savings Plans
          • SCPs: maximum permissions for accounts in an OU (don't grant anything)
          • Control Tower: sets up a multi-account landing zone with guardrails
          • RAM: share subnets, Transit Gateways and more across accounts

          Service Quotas

          limits

          Per account, per Region (e.g. vCPUs for On-Demand instances, Elastic IPs). Request increases in the Service Quotas console; alarm on usage with CloudWatch. "Can't launch more instances" with no other error → a quota.

          Pricing basics

          billing

          Pay as you go, pay less when you commit (Savings Plans, RIs), pay less per unit at volume. Data into AWS is free; data out to the internet costs. Estimate with the Pricing Calculator.

          Support plans

          changing

          Basic is free. Paid plans add 24/7 engineers, faster response and the full Trusted Advisor checks. AWS is retiring Developer, Business and Enterprise On-Ramp on 1 Jan 2027 in favour of Business Support+ and Enterprise Support (designated TAM, 15-minute critical response). SAA-C03 rarely asks about plans.

          Lesson 6 · 10 min

          The six Well-Architected pillars

          The exam's four domains map onto these pillars. Answers that follow the design principles are usually the right ones.

          Operational excellence

          run it

          Infrastructure as code, small reversible changes, runbooks, learn from failures.

          Security

          domain 1 · 30%

          Strong identity, least privilege, traceability, security at every layer, encrypt data in transit and at rest.

          Reliability

          domain 2 · 26%

          Recover automatically, scale horizontally, stop guessing capacity, test recovery.

          Performance efficiency

          domain 3 · 24%

          Use managed and serverless services, go global in minutes, experiment, pick the right resource type.

          Cost optimization

          domain 4 · 20%

          Pay only for what you use, measure efficiency, stop spending on undifferentiated heavy lifting.

          Sustainability

          newest

          Maximize utilization, use managed services and efficient hardware (Graviton), reduce data you keep and move.

          Which pillar?

          Pick a practice.

          AWS Well-Architected Tool (free, in the console) runs a review of a workload against the pillars and tracks the risks you find.
