    Six ways for services to talk

    Synchronous calls wait for an answer and fail together. Asynchronous messages let each part run, scale and fail on its own. The exam nearly always prefers async for decoupling.

    PatternServiceOne-line idea
    QueueSQSProducers drop work in; one worker takes each message
    Pub/subSNSOne message pushed to many subscribers at once
    Event busEventBridgeRoute events by their content to the right targets; AWS and SaaS events built in
    OrchestrationStep FunctionsA state machine runs steps in order, with branches, retries and waits
    StreamKinesis / MSKOrdered, replayable records for many readers (see Analytics Playbook)
    API front doorAPI Gateway / AppSyncSynchronous REST, WebSocket or GraphQL entry point
    BrokerAmazon MQManaged ActiveMQ / RabbitMQ for apps using standard protocols

    Which one?

    Choreography vs orchestration. With SNS or EventBridge, each service reacts to events on its own (choreography). With Step Functions, one state machine tells each step what to do (orchestration). Need retries, order and one place to see progress → Step Functions.

    SQS: the queue

    A consumer receives a message, which hides it for the visibility timeout. If the consumer deletes it in time, it's done. If not, it reappears for another try.

    Message lifecycle simulator

    Consumer

    Light band = message hidden (visibility timeout). Bar = a worker processing it. Orange = duplicate work. Red = worker crashed.

    Standard queueFIFO queue
    OrderBest effortStrict, per message group ID
    DeliveryAt least once (rare duplicates)Exactly-once processing (dedup within 5 minutes)
    ThroughputNearly unlimited300 msg/s per action, 3,000 with batching; high-throughput mode for much more
    NameAnyMust end in .fifo
    DedupMake consumers idempotentDeduplication ID or content-based deduplication

    FIFO parallelism: different message group IDs are processed in parallel; one group is always in order. Use the customer or order ID as the group ID.

    Settings

    • Visibility timeout: default 30 s, up to 12 h. Workers can extend it with ChangeMessageVisibility
    • Retention: 1 min – 14 days (default 4 days)
    • Delay queue: hide new messages up to 15 min
    • Long polling: wait up to 20 s for messages; fewer empty responses, lower cost

    Dead-letter queue

    After maxReceiveCount failed receives, the message moves to a DLQ for inspection. Fix the bug, then redrive messages back to the source queue. A FIFO queue needs a FIFO DLQ.

    Scaling consumers

    • ASG target tracking on backlog per instance
    • Lambda event source mapping: batches, scales with queue depth, partial batch responses

    Security & size

    • Encryption: SSE-SQS or KMS, HTTPS in transit
    • Access policy for cross-account senders or SNS topics
    • Large payloads: put the body in S3 and send a pointer (Extended Client Library)

    SNS: one message, many receivers

    Publishers send to a topic. SNS pushes a copy to every subscriber whose filter policy matches.

    Fan-out with filters

    Publish an event

    Subscribers

    SQS, Lambda, HTTP/S endpoints, email, SMS, mobile push, Data Firehose.

    Filter policies

    Match on message attributes or the message body. Without a filter, a subscriber gets everything.

    FIFO topics

    Ordered, deduplicated fan-out to SQS queues. Pair with SQS FIFO for order end to end.

    Reliability

    Retries per protocol, DLQ per subscription. SNS doesn't store messages for later; add SQS subscribers so consumers can catch up.

    SQSSNS
    ModelPull (consumers poll)Push to subscribers
    Receivers per messageOneMany
    PersistenceUp to 14 daysNo storage (deliver and retry)
    Best answer when"buffer", "decouple workers", "process later""notify", "fan out", "send to email/SMS"
    SNS + SQS fan-out is the classic answer when one event must be processed by several services independently and reliably: SNS for the copies, SQS so each service can be slow or offline without losing messages.

    EventBridge: route events by what they contain

    Events land on an event bus. Rules match event patterns and send matches to targets.

    Rule matcher

    Incoming event

    Event buses

    • Default: events from AWS services (EC2 state change, S3, CodePipeline, Health…)
    • Partner: SaaS events (Zendesk, Datadog, Shopify…)
    • Custom: your apps' events
    • Send to buses in other accounts or Regions

    Targets

    Lambda, SQS, SNS, Step Functions, Kinesis, Firehose, ECS tasks, CodeBuild, SSM Automation, another event bus, and any HTTP API (API destinations). Input transformers reshape the event.

    Scheduler

    Cron, rate or one-time schedules, with time zones and retries, for millions of schedules. Replaces "EC2 running cron".

    Pipes

    Point-to-point: source (SQS, Kinesis, DynamoDB Streams, MSK, MQ) → filter → enrich → target. Less glue code than Lambda.

    Archive & replay

    Keep events and replay them later, e.g. after fixing a bug in a consumer.

    Schema registry

    Discovers event structures and generates code bindings.

    EventBridge or SNS? React to AWS service or SaaS events, route by many fields, schedules, replay → EventBridge. Very high-throughput fan-out to many subscribers, SMS, email, mobile push → SNS.

    Step Functions: workflows as state machines

    You draw the steps; Step Functions runs them, retries failures, waits, branches, and records every step of every run.

    Order workflow

    Order amount
    Payment service
    Standard workflowExpress workflow
    Max duration1 year5 minutes
    ExecutionExactly onceAt least once (async) / at most once (sync)
    HistoryFull visual history in the consoleCloudWatch Logs
    PricePer state transitionPer execution and duration
    Use forLong, auditable business processes, human approvalHigh-volume, short event processing, IoT, streaming

    State types

    Task (do work), Choice (branch), Parallel, Map (for each item), Wait, Pass, Succeed, Fail. Retry and Catch on any Task.

    Integration patterns

    • Request-response: call and move on
    • Run a job (.sync): wait for ECS, Glue, Batch to finish
    • Wait for callback (task token): pause until a human or system replies

    SDK integrations

    Call 200+ AWS services directly (DynamoDB, SNS, S3…) without a Lambda in between. Distributed Map runs thousands of parallel steps over S3 objects.

    Limits & protection

    • Account throttle: 10,000 requests/s (burst 5,000) per Region by default
    • Per-client throttling with usage plans
    • Integration timeout about 29 s by default; long jobs go async

    Endpoint types

    Edge-optimized (via CloudFront), Regional, Private (only from a VPC via interface endpoint).

    Direct integrations

    API Gateway can call SQS, Step Functions, DynamoDB or Kinesis directly, without Lambda in the middle.

    The rest

    AppSync

    GraphQL

    Managed GraphQL APIs that combine data from DynamoDB, Lambda, RDS and HTTP. Real-time subscriptions and offline sync for mobile apps.

    Amazon MQ

    broker

    Managed ActiveMQ and RabbitMQ. Supports MQTT, AMQP, STOMP, OpenWire, JMS. For migrating existing apps without rewriting. Active/standby across AZs. Less scalable than SQS/SNS.

    AppFlow

    SaaS data

    No-code data transfer between SaaS apps (Salesforce, SAP, Zendesk, Slack) and AWS (S3, Redshift), on a schedule or on events.

    Lambda async

    retries

    Async invocations retry twice. Send results to destinations (on success or failure: SQS, SNS, Lambda, EventBridge) or failures to a DLQ.

    SES

    email

    Send and receive email at scale: transactional, marketing. SNS email is only for simple notifications.

    SWF

    legacy

    Simple Workflow Service. Older; on the exam Step Functions is almost always the better answer, unless "external signals" and existing SWF code.
