    Every exam question is really asking one of five things

    Most SAA questions end with "MOST cost-effective", "LEAST operational overhead", "highly available", "most secure" or "best performance". That last phrase decides the answer.

    Well-Architected Framework: 6 pillars

    Operational ExcellenceAutomate, infrastructure as code, small reversible changes, learn from failures.
    SecurityLeast privilege, traceability, security at every layer, encrypt in transit and at rest.
    ReliabilityRecover automatically, scale horizontally, test recovery, stop guessing capacity.
    Performance EfficiencyUse managed and serverless services, go global in minutes, experiment.
    Cost OptimizationPay for what you use, measure, use the cheapest model that fits.
    SustainabilityUse only what you need, right-size, use efficient hardware like Graviton.

    Principles behind the right answers

    Design for failure

    Everything fails eventually. Spread across at least 2 AZs and remove single points of failure.

    Stateless tiers

    Keep sessions and files outside instances (ElastiCache, DynamoDB, S3, EFS). Then any instance can be replaced or added.

    Loose coupling

    Put a queue or event bus between components so one slow or failed part doesn't break the others.

    Scale out, not up

    Many small instances behind a load balancer beat one big instance: no downtime to resize, no single failure.

    Managed beats self-managed

    "Least operational overhead" almost always means a managed or serverless service, not software you run on EC2.

    Automate

    CloudFormation or CDK for infrastructure, Auto Scaling for capacity, EventBridge + Lambda / SSM for responses.

    RTO and RPO

    RPO: how much data can you lose?

    Recovery Point Objective. Time between the last good copy and the disaster. Backups every 24 h → RPO up to 24 h. Continuous replication → seconds.

    RTO: how long can you be down?

    Recovery Time Objective. Time from the disaster until service is back. Restore from backup → hours. Standby already running → minutes.

    Lower RTO and RPO always cost more. The exam wants the cheapest design that still meets the stated numbers. Don't pick active/active when "4 hours" is acceptable.

    The classic highly available web app

    Route 53 → CloudFront → ALB → Auto Scaling group in 2+ AZs → ElastiCache → RDS Multi-AZ. Static files in S3.

    Failure simulator

    Choose your design, then break something. Single resources are assumed to be in AZ-a.

    Break something

    Multi-AZ vs multi-Region

    Multi-AZ protects against a data center failure and is the normal "highly available" answer. Multi-Region is for disaster recovery, global latency or data residency, and costs more.

    Static content

    Images, CSS and JS go to S3 + CloudFront, not the web servers. Less load, cheaper, faster.

    Shared files

    Instances that need the same files use EFS (Linux) or FSx (Windows), not copies on each EBS volume.

    Health checks everywhere

    Route 53 health checks between Regions, ALB health checks between instances, ELB health checks on the ASG.

    Lesson 3 · 12 min · heavily tested

    Four disaster recovery strategies

    From cheap and slow to expensive and instant. Set the RTO and RPO; the cheapest strategy that meets both lights up.

    StrategyWhat runs in the DR RegionRecovery steps
    Backup & restoreNothing. Only backups and AMIs copied thereDeploy with IaC, restore data, switch DNS
    Pilot lightCore data replicated live (DB replica). App servers off or not createdStart/create app servers, scale up, promote DB, switch DNS
    Warm standbyA full copy of the stack running at small scaleScale out, promote DB, switch DNS
    Multi-site active/activeFull production in 2+ Regions, all taking trafficRoute 53 or Global Accelerator stops sending to the failed Region

    Tools for DR

    • AWS Backup: cross-Region, cross-account copies
    • Aurora Global Database: replication usually under 1 s, promote a secondary in about a minute
    • DynamoDB global tables: multi-active writes in many Regions
    • S3 CRR, EBS snapshot copy, AMI copy

    AWS Elastic Disaster Recovery

    Continuously replicates on-prem or cloud servers at block level into a low-cost staging area. Launch recovered instances in minutes. RPO of seconds, RTO of minutes.

    Failover routing

    Route 53 failover policy with health checks, or Global Accelerator for faster failover without waiting for DNS caches.

    When the front end calls the back end directly, a spike or an outage in one breaks both. A queue absorbs the spike and the workers catch up later.

    Which messaging service?

    ServiceModelUse it when
    SQS StandardQueue, pull. At-least-once, best-effort order, nearly unlimited throughputBuffer work for workers; decouple tiers
    SQS FIFOQueue with strict order and exactly-once processing. 300 msg/s per action (3,000 batched); high-throughput mode for moreOrder matters: payments, order events

    EventBridgeEvent bus with rules, filtering, schedules, SaaS sources, archive and replayReact to AWS or SaaS events; route by content; cron jobs

    Data FirehoseManaged delivery, buffers and loads dataLoad streams into S3, Redshift, OpenSearch, Splunk with no code
    Step FunctionsWorkflow state machine with retries, branches, waits, human approvalOrchestrate several steps or Lambdas
    Amazon MQManaged ActiveMQ / RabbitMQMigrating apps that use MQTT, AMQP, JMS

    SQS settings to know

    • Visibility timeout (default 30 s, max 12 h): message hidden while a worker processes it. Too short = processed twice
    • Dead-letter queue: after N failed receives
    • Long polling (up to 20 s): fewer empty responses, lower cost
    • Delay queue: up to 15 min
    • Retention 4 days default, max 14

    Fan-out pattern

    SNS topic → several SQS queues. Each consumer gets its own copy and works at its own pace. Use SNS message filtering to send each queue only what it needs.

    Scale workers on the queue

    Auto Scaling group with target tracking on a custom metric: backlog per instance (ApproximateNumberOfMessagesVisible ÷ instances). Or Lambda with an SQS trigger.

    Serverless patterns

    Serverless API

    API Gateway → Lambda → DynamoDB. Cognito for sign-in. Scales to zero, pay per request.

    File processing

    S3 upload → event → Lambda (or SQS → Lambda for buffering and retries) → results to S3 or DynamoDB.

    Static website

    S3 + CloudFront (OAC) + Route 53 alias + ACM certificate in us-east-1.

    Scheduled jobs

    EventBridge Scheduler → Lambda (under 15 min) or ECS Fargate task (longer).

    Multi-step workflow

    Step Functions coordinates Lambdas with retries and error handling instead of Lambdas calling Lambdas.

    Real-time stream

    Kinesis Data Streams → Lambda or Managed Service for Apache Flink → S3 via Firehose.

    Lambda facts

    • Timeout max 15 minutes
    • Memory 128 MB – 10 GB (CPU scales with it)
    • /tmp up to 10 GB
    • Provisioned concurrency removes cold starts
    • Reserved concurrency caps or guarantees one function
    • In a VPC: use RDS Proxy for databases

    API Gateway facts

    • REST, HTTP (cheaper, simpler) and WebSocket APIs
    • Throttling, usage plans, API keys
    • Response caching (REST APIs)
    • Edge-optimized, Regional or private endpoints
    • Integration timeout about 29 s by default

    Containers facts

    • Task role: IAM role per ECS task
    • ECR stores images
    • ECS Service Auto Scaling for tasks; capacity providers for hosts
    • Persistent shared storage: EFS
    Lesson 6 · 12 min

    Make reads cheap and fast

    Cache at every layer the user passes through, from the edge to the database.

    LayerServiceCaches
    EdgeCloudFrontStatic files, whole pages, API responses near users
    APIAPI Gateway cachingResponses for a TTL (REST APIs)
    ApplicationElastiCache (Redis OSS / Valkey / Memcached)Query results, sessions, leaderboards
    DynamoDBDAXMicrosecond reads in front of DynamoDB, no code changes to logic
    Relational DBRead replicasOffload read-heavy queries and reports

    Lazy loading (cache-aside)

    Read cache → miss → read DB → write to cache. Only requested data is cached. Data can go stale; the first read is slow.

    Write-through

    Every DB write also updates the cache. Never stale, but every write costs more and unused data fills the cache. Add a TTL either way.

    Redis OSS / Valkey

    Replication, Multi-AZ failover, backups, persistence, sorted sets (leaderboards), pub/sub.

    Memcached

    Simple, multi-threaded, sharding. No replication, no persistence.

    Multi-AZ vs read replicas

    RDS Multi-AZ (instance)Read replica
    PurposeHigh availabilityRead scaling (and DR if cross-Region)
    ReplicationSynchronousAsynchronous
    Can you read from it?No, standby onlyYes
    FailoverAutomatic, same endpoint, about 1–2 minManual promotion, new endpoint
    LocationAnother AZ, same RegionSame AZ, another AZ, or another Region

    RDS Multi-AZ DB cluster (MySQL, PostgreSQL) has two readable standbys. Aurora always stores 6 copies across 3 AZs and allows up to 15 replicas behind a reader endpoint.

    RDS Proxy

    Pools database connections. Fixes "too many connections" from Lambda, speeds up failover, supports IAM auth.

    Global data

    Aurora Global Database: one writer Region, fast cross-Region reads and DR. DynamoDB global tables: write in any Region.

    Session state

    Prefer ElastiCache or DynamoDB over ALB sticky sessions. Then any instance can serve any user.
