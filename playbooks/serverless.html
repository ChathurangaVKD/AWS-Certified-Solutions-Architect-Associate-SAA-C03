    LimitValueExam consequence
    Max timeout15 minutesLonger jobs → Fargate, Batch, or Step Functions splitting the work
    Memory128 MB – 10,240 MBCPU scales with memory; more memory can make it faster and cheaper
    /tmp storage512 MB – 10,240 MBBig files → S3 or EFS mount
    Package size50 MB zipped upload, 250 MB unzippedBigger → container image (up to 10 GB) or layers
    Concurrency1,000 per Region (default, raisable)Shared by all functions → reserved concurrency protects critical ones
    Sync request/response payload6 MBLarge data → pass an S3 key, not the data

    Reserved concurrency

    cap + guarantee

    Sets aside N for one function and caps it at N. Protects a database from being overwhelmed and protects other functions from starvation.

    Provisioned concurrency

    no cold starts

    Keeps N environments initialized. "Consistent low latency", "cold starts are a problem" → provisioned concurrency (or SnapStart for Java, Python, .NET).

    Configuration

    ops

    Environment variables (encrypt with KMS), layers for shared libraries, versions and aliases for safe rollouts (weighted alias = canary).

    Concurrency calculator

    Concurrent executions needed
    Available to this function

    Concurrency = requests per second × duration in seconds. The default Regional limit is 1,000 shared by every function in the account.

    How Lambda is invoked, and what happens on failure

    ModelSourcesOn error
    SynchronousAPI Gateway, ALB, function URL, SDK invoke, CognitoError returns to the caller; caller retries
    AsynchronousS3 events, SNS, EventBridge, CloudWatch LogsLambda retries 2 more times, then sends to a DLQ or on-failure destination
    Event source mapping (polling)SQS, Kinesis, DynamoDB Streams, MSKSQS: message returns after visibility timeout, then DLQ on the queue. Streams: retries block the shard until success or expiry

    SQS + Lambda

    tuning
    • Queue visibility timeout ≥ 6× the function timeout
    • Report partial batch failures so good messages aren't retried
    • Redrive policy on the queue → DLQ
    • FIFO queue keeps order per message group

    Lambda in a VPC

    trap
    • Attach to private subnets to reach RDS, ElastiCache
    • It then has no internet unless the subnets route to a NAT gateway
    • Reach S3/DynamoDB through VPC endpoints
    • Many short connections to RDS → RDS Proxy

    At the edge

    CloudFront

    CloudFront Functions: tiny JavaScript, viewer request/response, header rewrites, URL redirects. Lambda@Edge: Node/Python, all four triggers, network calls, longer runtime.

    Orchestration

    beyond 15 min

    Step Functions chain Lambdas with retries, branches, waits up to a year, and human approval. Distributed Map fans out over millions of S3 objects.

    Lesson 4 · 14 min · heavily tested

    Containers on ECS

    Task definition

    blueprint

    Image, CPU/memory, ports, environment, secrets, log config, IAM roles, network mode. A task is a running copy.

    Service

    keeps N running

    Maintains the desired count, replaces failed tasks, registers them with an ALB/NLB target group, scales with Application Auto Scaling (CPU, memory, ALB requests per target).

    Launch types

    who runs hosts
    • EC2: you run the container instances (ASG via capacity provider)
    • Fargate: no hosts; pay per task vCPU/GB
    • Fargate Spot: up to ~70% off, interruptible

    Networking

    awsvpc

    In awsvpc mode (required on Fargate) every task gets its own ENI and private IP, so security groups apply per task.

    Storage

    state

    Containers are ephemeral. Shared persistent files → mount EFS (works with Fargate). Put state in RDS/DynamoDB/S3.

    ECR

    registry

    Private image registry: image scanning, lifecycle policies to delete old images, immutable tags, cross-Region and cross-account replication.

    Task role or task execution role?

    The execution role is used by the ECS agent to start the task. The task role is used by your code inside the container. Click each permission to sort it.

        Lesson 5 · 10 min

        EKS, App Runner, Beanstalk, Batch

        EKS

        Kubernetes
        • AWS runs the control plane
        • Workers: managed node groups, self-managed nodes, or Fargate profiles (no nodes)
        • Pods get AWS permissions via IAM roles for service accounts / Pod Identity
        • Choose it when the team already uses Kubernetes or needs portability

        App Runner

        simplest web app

        Point it at a container image or source repo; get an HTTPS URL with automatic scaling and load balancing. No cluster, no ALB to configure.

        Elastic Beanstalk

        PaaS on EC2

        Upload code; it creates EC2, ASG, ELB and monitoring. Deployment policies: all at once, rolling, rolling with additional batch, immutable, traffic splitting; blue/green by swapping environment URLs.

        AWS Batch

        jobs

        Queues and runs batch jobs on EC2, Spot or Fargate; sizes compute automatically. No 15-minute limit.

        Step Functions

        workflow

        Standard workflows (long, exactly-once) vs Express (high-volume, short). Integrates with 200+ services directly.

        Lightsail

        simple VPS

        Fixed monthly price bundles for simple sites and small apps; little AWS knowledge needed.

        Least operational overhead ladder: Lambda / App Runner / Fargate < Beanstalk < ECS or EKS on EC2 < plain EC2. If the question says "Kubernetes", stay on EKS even if Fargate seems simpler.
